# Plugin packaging and intake proof

Status: implemented packaging and intake boundary. The author-facing CLI now compiles source projects into this normalized format, while upload and staging reuse the same non-executing validator.

## Normalized package input

The packer consumes build output, not a framework's arbitrary `dist/` folder.
Only these paths are accepted:

```text
manifest.json
license.txt                         # optional
browser/**                          # optional built HTML/JS/CSS/assets
server/**                           # optional normalized handler bundle
data/**                             # optional static schema
schemas/**                          # optional public contracts
assets/**                           # optional package metadata
```

`package.json`, `node_modules`, source manifests, TypeScript configuration,
install scripts, and files outside the normalized roots are rejected. Symlinks
and non-regular input files are rejected. `integrity.json` is generated by the
packer and cannot be supplied by the build directory.

The internal proof command is:

```bash
pnpm plugin:pack <normalized-directory> <output.launch-plugin>
```

The same deterministic writer is now shared by `launchpp pack`; this command remains available for repository-level normalized-package proofs.

## Deterministic archive

The `.launch-plugin` file is ordinary ZIP with a product-specific contract.
The packer sorts paths, fixes ZIP timestamps and file attributes, uses fixed
compression settings, emits canonical integrity JSON, and includes no host
filesystem timestamps. The package hash is SHA-256 over the final archive
bytes. Identical file bytes and paths therefore produce identical archive
bytes and hashes.

`integrity.json` v1-preview records the SHA-256 digest and expanded size of every file except itself exactly once; the retained legacy v0 proof records the same complete digest coverage without sizes. Intake verifies the manifest contract and each digest before staging.

## Non-executing intake

Archive intake is data processing only. It does not invoke npm, pnpm, Bun,
Node, TypeScript, Vite, package scripts, or plugin code. Before expansion it
enforces limits on compressed bytes, entry count, per-entry expanded bytes,
total expanded bytes, and compression ratio. It rejects:

- absolute paths, traversal, backslashes, empty/dot segments, and unexpected
  roots;
- duplicate and case-colliding names;
- unsupported/corrupt ZIP data;
- missing, incompatible, or malformed manifests;
- incomplete, extra, or incorrect integrity entries; and
- archives outside configured resource limits.

Validated bytes are written as ordinary non-executable files to a fresh
staging directory under the installation root. A same-filesystem rename moves
the complete tree to
`<plugin-id>/<version>/<archive-sha256>`. The content-addressed destination is
immutable and reinstalling the same bytes is idempotent. Failed staging is
removed without exposing a partial installation.

## Executable evidence

Tests prove byte-for-byte repeatability after source mtime changes, full digest
coverage, tamper rejection, traversal rejection before installation, ZIP-bomb
limits, lifecycle-script rejection without execution, atomic installation,
idempotency, and successful installation with an empty `PATH` (no compiler or
package manager available).

Archive upload streaming, persistent installation records, provenance/signing,
rollback UI, and operator recovery are later lifecycle work. Those features
must call this boundary rather than creating a second extractor.
